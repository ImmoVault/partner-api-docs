Reference

MCP server reference

The messpunkt.io MCP server lets landlords ask their own AI assistant about their properties, consumption and devices. It is read-only, uses the same authorization server and consent screen as the REST API, and applies the same data rules. Landlords who just want to connect should read Mit Claude, ChatGPT oder Codex verbinden (German).

Not live yet. The MCP server is part of V1 and goes live together with the production REST API, announced in the changelog. There is no sandbox MCP server.

Endpoints

URL
MCP endpoint (resource)https://mcp.messpunkt.io/v1
Protected resource metadata (RFC 9728)https://mcp.messpunkt.io/.well-known/oauth-protected-resource/v1
Authorization serverhttps://auth.messpunkt.io (metadata at https://auth.messpunkt.io/.well-known/oauth-authorization-server)

Transport

  • Streamable HTTP, stateless. Every JSON-RPC request is a POST to /v1 and is answered on its own. The server keeps no session between requests, so a client does not need sticky routing.
  • No server-initiated requests in V1: the read-only tools never ask the client for input (no elicitation, no sampling).
  • Requests with an Origin header must come from an allowed origin, otherwise 403. Clients that send no Origin (desktop and server clients) are not affected.
  • Request bodies are limited to 1 MiB (413 above).

Authorization

OAuth 2.1 Authorization Code with PKCE (S256), exactly as for the REST API, with resource=https://mcp.messpunkt.io/v1 (RFC 8707). The access token's aud is that resource. A REST token is rejected here and vice versa.

  • Client registration: Client ID Metadata Documents. An MCP client identifies itself with an https URL as client_id pointing to its metadata document (token_endpoint_auth_method: none). The authorization server advertises client_id_metadata_document_supported: true and none in token_endpoint_auth_methods_supported. Dynamic client registration is not offered. Claude, Claude Code, Codex and ChatGPT document CIMD support; Claude uses CIMD exactly when both values are advertised (Anthropic: authentication for connectors). None of these clients has been tested live against this server yet.
  • Redirect URIs are matched exactly for https. Loopback redirects (http://localhost, http://127.0.0.1, http://[::1]) match with any port and exact path. The consent screen warns the landlord that such a client runs on their own computer.
  • Consent: the landlord picks the customer organisation and all Properties, including future ones or a selection. The token carries that selection; tools outside it behave as if the Property did not exist.
  • Connection check on every request: after the landlord disconnects in the portal, requests fail within 60 seconds.
  • DPoP-bound tokens (RFC 9449) are accepted with Authorization: DPoP and a proof, as on the REST API.

Auth challenge

Without a token the server answers 401 and points to its metadata:

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer scope="read:units read:devices read:readings", resource_metadata="https://mcp.messpunkt.io/.well-known/oauth-protected-resource/v1"
Content-Type: application/problem+json

A rejected token adds error="invalid_token" and error_description. For a DPoP-bound token the scheme is DPoP with algs.

A tools/call for a tool whose scope the token lacks is refused before the tool runs, with a real HTTP 403 so the client can step up:

HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope", error_description="…", scope="read:devices", resource_metadata="https://mcp.messpunkt.io/.well-known/oauth-protected-resource/v1"
Content-Type: application/problem+json

The problem detail is German, for clients that show it to the landlord; it tells them to reconnect with that permission. Clients that support step-up authorization reopen the consent screen with the scope from WWW-Authenticate instead (Claude Code does). tools/list is not scope-filtered: every tool is listed, and its required scope is below.

Rate limits

Counted per connection (grant) over every authenticated request to /v1, not only tools/call; 429 with Retry-After above the limit. Production: 60 calls per minute per connection, counted in memory per server instance (the effective limit can be higher, never lower).

Tool behaviour

  • All tools are read-only (readOnlyHint: true, idempotentHint: true, openWorldHint: false). Each returns structured content matching its outputSchema plus a short text summary for clients that ignore structured content.
  • Tool and field names are English. Descriptions, summaries and error texts are German, because landlords read them. The reference below quotes them as delivered.
  • Properties can be named by ID or by a part of their name or address. If several match, the result lists the candidates instead of failing. “Not found” and “not shared with you” produce the same answer.
  • list_properties pages with a cursor, with or without a search: query (part of the name or address, case-insensitive, % and _ taken literally) narrows the list, and the next page is fetched with the cursor of the previous answer and the same query. The cursor is not bound to the query, so a different query gives a shifted page, never other data.
  • get_property_overview returns difference_meter_count: difference meters have no value of their own and are missing from get_consumption and get_device_status; 0 means the difference-meter note in the tool descriptions does not apply to this Property.
  • Validation problems (for example a range longer than 36 months) come back as a tool result with isError: true and a German explanation, not as a protocol error.
  • Data rules as in the REST API: monthly values at the finest; one unit per metric (kWh, m3, unit = heat-cost-allocator units), never summed across metrics; water_outdoor separate; difference meters without a value; calibration status unknown never means “fine”.
  • Nothing is left out silently. get_consumption names the months of the range without values (months_without_values) and, when some are missing, the first month the Property has values at all (first_month_with_values). Measuring points of a requested metric that are not evaluated are listed in not_evaluated_measuring_points with a reason (today only no_system: assigned to no heating or water system); get_property_overview and get_device_status always list them. Clients must tolerate new reason values.
  • For one apartment, call get_consumption with usage_unit (name or ID); the result is broken down by usage unit and shows shared areas with their percentage in shared_sectors.

Versioning

The path carries the major version (/v1). Within v1 changes are additive only: new tools, new optional input fields, new output fields. A tool is never renamed or removed, and its meaning never changes. The server's test suite compares tools/list with a saved snapshot, so any change to a tool needs a deliberate snapshot update. The tool reference below is generated from that snapshot.

get_consumption

Verbrauch je Monat · scope read:readings · readOnlyHint: true · idempotentHint: true · destructiveHint: false · openWorldHint: false
Liefert Monatswerte des Verbrauchs einer Liegenschaft. Die Liegenschaft wird als property per Name, Adress-Teilstring oder ID angegeben; passen mehrere, kommt eine Kandidatenliste. Werte sind höchstens monatlich aufgelöst (nie Tages- oder Rohwerte) und jede Kennzahl hat ihre eigene Einheit: heat in kWh, hca in HKV-Einheiten (dimensionslos, Einheit unit), water_cold, water_warm und water_outdoor in m3, electricity in kWh. Aussenwasser (water_outdoor) wird getrennt von Kalt- und Warmwasser ausgewiesen; eine Summe über verschiedene Kennzahlen gibt es nicht. Zeitraum: from_month und to_month als JJJJ-MM; ohne Angabe die letzten 12 abgeschlossenen Monate, höchstens 36 Monate je Aufruf; der laufende Monat ist nie enthalten. breakdown wählt die Gliederung: systems (je Anlage, Standard), sectors (je Bereich einer Anlage) oder usage_units (je Nutzeinheit, anteilig nach Zuordnung der Bereiche). Fragt jemand nach einer Wohnung oder Nutzeinheit, breakdown=usage_units verwenden, mit usage_unit (Name oder ID) für genau eine Einheit. Mit include_devices=true kommen die Gerätesegmente dazu; deren baseline_origin sagt, woher der Startwert eines Tausch-Heizkostenverteilers stammt: recorded (erfasster Startwert), assumed_zero (angenommen 0, nicht erfasst), first_reading (erster Messwert nach Einbau; Verbrauch davor unbekannt), portal_rule (Stand zu Beginn des Zeitraums, wie im Portal) oder none (kein Startwert). Ein angenommener Startwert wird immer gemeldet. Jeder Monatswert trägt einen Status; calibration_expired heißt, ein Gerät mit abgelaufener Eichung trägt nichts zum Wert bei. Eichstatus unbekannt — das heißt nicht, dass die Eichung in Ordnung ist. Differenzzähler: kein Wert in V1. Benötigt das Recht read:readings.

get_device_status

Gerätestatus · scope read:devices · readOnlyHint: true · idempotentHint: true · destructiveHint: false · openWorldHint: false
Zeigt je Gerät einer Liegenschaft, ob es stumm ist (mehr als 7 Tage kein Funktelegramm), das Datum des letzten Empfangs, den Eichstatus (ok, expired, replaced, not_required, unknown) mit Ablaufdatum sowie Ein- und Ausbau bzw. Tausch. Die Liegenschaft wird als property per Name, Adress-Teilstring oder ID angegeben; passen mehrere, kommt eine Kandidatenliste. Mit only_problems=true erscheinen nur stumme Geräte und Geräte mit abgelaufenem oder unbekanntem Eichstatus. Ausgebaute Geräte erscheinen nur mit include_removed=true. Eichstatus unbekannt — das heißt nicht, dass die Eichung in Ordnung ist. Der letzte Empfang ist nur als Datum angegeben. Differenzzähler: kein Wert in V1. Benötigt das Recht read:devices.

list_properties

Liegenschaften auflisten · scope read:units · readOnlyHint: true · idempotentHint: true · destructiveHint: false · openWorldHint: false

Mit query (Teil des Namens oder der Adresse, Groß-/Kleinschreibung egal, Zeichen wie % gelten wörtlich) werden nur die passenden Liegenschaften gelistet.
